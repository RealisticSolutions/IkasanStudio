## Critical ActiveMQ alert #1

`studio-bundled-packs:activeMqTestRuntimev3` imported `org.ikasan:ikasan-eip-standalone-bom:3.3.9` and selected `activemq-client:5.16.3`. That version is genuinely vulnerable to CVE-2023-46604. The [Apache advisory](https://activemq.apache.org/security-advisories.data/CVE-2023-46604-announcement.txt) covers both clients and brokers: absence of a broker in the plugin does not make the vulnerable test client safe.

The separate V4 configuration selected `activemq-client:6.2.1` from the 4.1.6 BOM, affected by alerts #5 and #7. V3 is repaired to **5.19.5** (Java 11 and `javax.jms`); V4 to **6.2.4** (Java 17 and `jakarta.jms`). These versions also address the newer [ActiveMQ TLS denial-of-service advisory](https://activemq.apache.org/security-advisories.data/CVE-2026-39304-announcement.txt). Moving V3 to ActiveMQ 6 would break its JMS namespace contract.

ActiveMQ is absent from the plugin runtime, adapter and offline distribution. It is used in isolated Studio tests, **and generated JMS applications depend on it at runtime**. Consequently both Spring JMS consumer and producer descriptors now explicitly version the client and broker, with matching documented `compatibilityOverrides` in each pack manifest. Regeneration updates existing old direct versions. The isolated provider test reads its client version from the same manifest and fails if the override is missing or duplicated. It keeps broker/Jackson dependencies out of the helper's isolated client classpath.

Maven resolution with the actual Ikasan BOMs plus the same direct JMS dependencies confirms client, broker and `activemq-openwire-legacy` all resolve to 5.19.5 / 6.2.4. The corresponding API artifacts are `jakarta.jms-api:2.0.3` (which contains `javax.jms`) and `jakarta.jms-api:3.1.0` (which contains `jakarta.jms`).

## Remaining ownership boundaries and upstream work

Apply shared commit `59237e83665bc03195792f6bfd72218ab808b256` to upstream Studio. It carries the buildscript Jackson/jsoup repairs, separate fixture Jackson/AssertJ repairs, V3/V4 client and broker metadata overrides, manifest-driven provider test versions and regeneration regression. Cherry-pick it in the upstream checkout and rerun the same gates against that checkout's versions. This document belongs to the community audit commit and is not needed upstream.

The approved Ikasan reference trees confirm their parent `version.activemq` values are still 5.16.3 (V3) and 6.2.1 (V4). **Ikasan EIP itself should publish matching BOM updates for client, broker and other ActiveMQ modules**; remove Studio's temporary overrides once each matching pack BOM manages patched versions. Reference repositories were read, not edited.

Generated V3 JMS application Maven resolution still inherits **Jackson core/databind 2.13.2** from its Ikasan 3.3.9 BOM; V4 inherits **2.22.0**. The V3 version falls within several older-family Jackson advisory ranges. The ActiveMQ repair does not constitute a full generated-application dependency security upgrade. A V3 Ikasan/Spring BOM compatibility upgrade remains needed; all V3 component combinations were not tested with a Jackson override, so no global generated-application Jackson pin was introduced in this Studio alert fix.

**IntelliJ-owned libraries remain a separate concern.** Inspection of supplied IDE JARs found Jackson core 2.17.0/databind 2.17.2 and jsoup 1.18.1 inside 2024.3.7 `lib-client.jar`; inspected 2026.2.2 IDE libraries contain Jackson 2.19.0 and jsoup 1.22.1. These values fall within relevant advisory ranges. They are not distributed by Studio and were not replaced or modified. A successful plugin verifier run does not prove those host libraries are secure or establish their reachability. JetBrains updates and validation against the updated IDE distribution are required for host remediation; shipping a second jsoup or replacing IDE JARs would not reliably fix the IDE's own classloader paths.

The 35 repository alerts are accounted for, and their effective Studio-controlled configurations select patched versions. This is not a claim that every dependency in every host IDE or generated Ikasan application is patched, nor that GitHub has closed the alerts before these commits are pushed and rescanned.
